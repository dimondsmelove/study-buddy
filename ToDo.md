### DECISION — принято пользователем

- Цель — минимальный backend для первого публичного выпуска, без стремления довести весь продукт до идеального состояния. Ориентир обсуждения — выпуск в течение пары недель; это не обещанная дата готовности или одобрения магазина. Смысл и структура UI сохраняются, пользователь позднее дополнит точечные замечания.
- Первый backend работает через OpenRouter. Прямой DeepSeek отложен. Существующий fallback сохраняется как исходное поведение; изменение маршрутов требует обоснования по актуальной доступности.
- Ключ разработчика остаётся только на сервере; публичное расширение не содержит provider key и не требует ключа пользователя. Текущий частный direct-provider запуск — отдельное временное исключение для личного использования.
- Переписка и изображения остаются в браузере, в существующем локальном хранилище; серверное хранение истории и cloud sync не нужны для этого выпуска. Backend временно обрабатывает контекст для вызова модели. Не сохранять prompt/image в серверную БД и обычные логи без нового решения.
- Фактический usage от OpenRouter сохраняется с ответом в браузере. Это уже поддерживается через `Turn.usage`; не создавать параллельную систему пользовательской статистики.
- Для первого релиза пользователь принял направление без токенизатора: приблизительная оценка контекста с запасом, фактические токены и стоимость — из API. Не переносить модельный словарь на backend как обязательную часть работы.

### HYPOTHESIS — предлагаемый минимальный объём, ещё не принятые требования

- Один небольшой сервис и одно необходимое служебное хранилище; существующие prompts/API/fallback переиспользовать. Не добавлять отдельные очереди, микросервисы, биллинг, аккаунты или облачную историю для будущих возможностей.
- Анонимная серверная сессия без видимой регистрации; сервер проверяет срок и применяет cooldown. Сессия не является уникальным человеком, сброс установки возможен.
- Дополнительные меры: ограничить выпуск сессий, одну активную генерацию на сессию и общий параллелизм; привязать request ID к содержимому, исключить повторный paid start; сохранить per-task output caps; добавить операторский выключатель генераций. Эти меры предложены primary, пользователь ещё не утвердил конкретный набор/значения.
- Сервер контролирует модели, prompts, параметры и размеры payload; не доверяет клиентскому счётчику, выбранному endpoint или присланной системной роли. Формат и число изображений валидируются до обращения к провайдеру; произвольные URL не скачиваются сервером.
- Простой streaming endpoint возвращает окончательный состав контекста первым событием, затем текст и финальные usage/status. Отдельный `/context/prepare` не является обязательным. Оценка до отправки и точная семантика Details требуют согласования.
- На сервере остаётся минимальное operational state для sessions/rate/idempotency/active requests и выбранной диагностики. Если нужны расходные ограничения, их источник истины — сервер; браузерный счётчик их не защищает. Подробная токенная история каждого чата в серверной БД не нужна сама по себе.
- Локальная реализация и проверка предшествуют внешнему deployment. Домашний ноут подходит как кандидат для dev; для публичного запуска primary рекомендует внешнее размещение. Fozzy упомянут пользователем как вариант, но хостинг/тариф/стек НЕ выбраны. VPS и managed-приложение имеют разный объём обслуживания.

## Проверенное исходное состояние — 2026-10-06, до loop

Исторические факты на базе исходного дерева до loop; ссылки/номера строк могут измениться. Актуальные реализованные контракты — в разделе локального среза выше.

- Расширение захватывает выделенную область экрана, делает crop и передаёт его в страницу чата. Captures хранятся в `chrome.storage.session`; старые ключи удаляются при превышении лимита **8** записей ([`service-worker.ts`](src/background/service-worker.ts#L183), [`messages.ts`](src/shared/messages.ts#L81)).
- Размер панели хранится в `chrome.storage.local`; настройки тоже локальны. Для диалогов и сообщений постоянного хранилища нет ([`overlay.ts`](src/content/overlay.ts#L180), [`settings.ts`](src/shared/settings.ts#L3)).
- Панель чата — встроенная extension page внутри overlay. При новом захвате она использует тот же iframe, если он ещё открыт. Кнопка закрытия удаляет host DOM вместе с этой страницей; массив `history` живёт только в её памяти и не сохраняется. Поэтому close уничтожает текущий контекст, а новое окно начинает новый transcript ([`overlay.ts`](src/content/overlay.ts#L216), [`overlay.ts`](src/content/overlay.ts#L325), [`chat.ts`](src/chat/chat.ts#L325)).
- Каждый пользовательский ход добавляется в `history`. Если установлен `activeImage`, его data URL добавляется к этому ходу; последующие запросы повторно включают полную историю, включая прежние изображения. Лимит в восемь capture-ключей не ограничивает рост `history` в живом iframe ([`chat.ts`](src/chat/chat.ts#L329), [`chat.ts`](src/chat/chat.ts#L509)).
- При невозможности связаться с overlay service worker открывает отдельное popup-окно. В коде этого fallback-пути нет восстановления уже открытой панели или сохранения истории между окнами ([`service-worker.ts`](src/background/service-worker.ts#L197)).
- `send()` блокирует пустой ввод и второй одновременный запрос, но не реализует интервал в 10 секунд ([`chat.ts`](src/chat/chat.ts#L509)).

В сборке с непустыми baked defaults пустые сохранённые `apiKey`/`baseUrl` могут пройти проверку, но уйти в gateway пустыми ([`settings.ts`](src/shared/settings.ts#L57), [`chat.ts`](src/chat/chat.ts#L106), [`chat.ts`](src/chat/chat.ts#L436), [`chat.ts`](src/chat/chat.ts#L451)). Значения ключей в этот документ не копируются.
- Маршрутизация текущих задач — `Solve`, `Quiz`, `Explain`, `Translate`, `Summarize`, свободный `Ask` и действие «Проще». Для задач есть локализованные шаблоны и параметры хода. `Hint` и `Check my work` в текущем наборе типов отсутствуют ([`prompts/index.ts`](src/shared/prompts/index.ts#L16), [`chat.ts`](src/chat/chat.ts#L533)).
- Текущий код запрашивает модель через `Gateway`, сейчас путь ведёт непосредственно к провайдеру. Локальное распознавание OCR из upstream OCR Buddy, согласно README, удалено; изображение отправляется vision-модели.

## Явные требования и рекомендации

| Категория | Содержание |
|---|---|
| Требование | Не чаще одного принятого запроса на 10 секунд; точная семантика границы для повторов/провайдерного fallback — открытый контракт D-03. |
| Требование | Не вводить lifetime quota вроде 50 вопросов. Это не запрещает временные анти-abuse меры и глобальный стоп расходов. |
| Требование | Сохранять диалог и возвращать тот же контекст; детали хранения, срока и закрытия — D-06/D-07. |
| Требование | Смена провайдера и модели должна оставаться за интерфейсом адаптера; обязательный пользовательский model picker не требуется. |
| Требование | Первые примерно два месяца без видимой регистрации; сроки не превращать в launch promise, а доступность pilot/public access решить отдельно в D-01. |
| Рекомендация | Для публичного использования оплачиваемый provider key держать на серверной стороне. Client-side cooldown полезен для UX, но не защищает общий ключ от модифицированного клиента. |
| Рекомендация | Использовать локальную БД для transcript и бинарных вложений (например, IndexedDB), а `chrome.storage.local` оставить для компактных настроек/индекса. **IndexedDB не утверждён пользователем**; выбор зафиксировать в TD-03. |
| Рекомендация | Хранить постоянную историю и отдельно строить ограниченный запросный контекст. Не полагаться на то, что провайдер «помнит» изображение между отдельными HTTP-запросами. |
| Рекомендация | Использовать сбрасываемую анонимную сессию, если это подходит решённому уровню защиты. ID установки не равен человеку и может быть сброшен; нельзя обещать идентификацию уникального пользователя. Не применять скрытый fingerprinting. |
| Рекомендация | Любой IP-сигнал рассматривать только как грубый анти-abuse сигнал с учётом общих школьных NAT; не выдавать его за пользовательский ID. |
| Рекомендация | Не сохранять учебный профиль и выводы об уровне ученика без отдельного продуктового решения. Диалог — это пользовательский материал, а не разрешение на долговременное profiling. |

### TD-01. Контракты продукта, анонимность и сбросы

**Приоритет:** P0 · **Статус:** ожидает решения · **Результат:** согласованный набор решений из реестра ниже. Это самостоятельная docs/architecture задача; она не разрешает реализацию.

**Зачем.** TD-03, TD-04, TD-05 и TD-06 зависят от решений о жизненном цикле данных, анонимной сессии и серверной границе. Без них можно сделать локальный прототип, но нельзя обещать безопасность общего оплачиваемого ключа или восстановление диалогов.

**Проверяемые критерии.**

- Для каждого решения D-01…D-12 записаны выбранный вариант, последствия и затронутые TD-ID либо явно оставлено `OPEN`.
- Для D-02 и D-05 есть ответственный за оплату/остановку и защита от неограниченного глобального расхода до public access либо public access заблокирован.
- Реестр не называет installation/session ID уникальным человеком и не обещает невозможность обхода анонимных лимитов.
- Ни одна запись не превращает настоящее docs-only разрешение в разрешение на код, реальный API, deploy или публикацию.

**Зависимости:** нет. Решения блокируют только указанные downstream-задачи. **Вопросы:** D-01…D-12; отдельные необязательные рекомендации могут остаться открытыми.

<a id="td-02"></a>
### TD-02. Надёжное разрешение настроек и первый запуск

**Приоритет:** P1 · **Статус:** завершено · **Результат:** фактически используемые настройки совпадают с теми, что проверила UI-логика; пользователь получает безопасное понятное состояние при пустом/ошибочном ключе.

**Зачем.** Сейчас baked defaults могут пройти `requireSettings()`, но не попасть в gateway при пустых сохранённых строках. Неисправный первый запрос маскирует состояние конфигурации.

**Объём.** Передавать единый разрешённый `Settings` объект от проверки до создания gateway. Задать приоритет: пользовательские параметры и разрешённые baked defaults; пустой keyless build не должен пытаться отправлять запрос. Ошибки не должны показывать ключ или его фрагменты. Проверить invalid URL, отсутствующий key, частично старую запись settings, переключение provider и сохранение.

**Не входит.** Не менять провайдера/модель, не добавлять onboarding с аккаунтом и не раскрывать ключ в интерфейсе или логах. Управление самим общим ключом относится к TD-06.

**Проверяемые сценарии.**

1. Сохранённый непустой BYOK и валидный URL создают gateway с этими значениями.
2. Пустые сохранённые поля в сборке с defaults используют разрешённые defaults по согласованному приоритету.
3. Пустые поля в сборке без baked key открывают настройки; сетевой вызов не начинается.
4. Неподдерживаемая схема URL остаётся на форме с понятной ошибкой; секреты отсутствуют в ошибке.
5. Ошибка storage или старый неполный объект не ломает доступ к форме настроек.

**Проверка:** unit/contract тесты на выбор настроек и mock gateway; без реального API. **Зависимости:** нет. **Открытый вопрос:** D-12 о том, какие provider/model metadata сохранять для диагностики; не блокирует исправление передачи настроек.

<a id="td-03"></a>
### TD-03. Сохранённые диалоги и хранилище вложений

**Приоритет:** P1 · **Статус:** завершено · **Результат:** закрытие приложения/iframe не уничтожает сохранённый диалог; записи и изображения имеют ясный локальный срок и способ удаления.

**Зачем.** История сейчас существует только в массиве памяти окна. Пользовательский запрос требует возвращаться к тому же контексту, а нынешнее ограничение восьми session crops не является хранилищем диалогов.

**Объём.** Определить модель `conversation`, `turn`, `attachment`, временные метки, статус ответа, локаль, prompt version и минимальную provider/model metadata для диагностики (если решение D-12 разрешит). Выбрать локальное хранилище; рекомендация — IndexedDB для растущих сообщений и Blob/data attachments, компактные настройки и индекс — в `chrome.storage.local`. Хранить ссылки/ID вложений в сообщениях, не копировать одну большую строку base64 в каждый ход. Мигрировать существующие settings без потери и без импорта ключей в transcript.

**Не входит.** Облачная синхронизация, серверные transcript, автоматическое извлечение постоянного student profile и неподтверждённый безлимитный срок хранения.

**Проверяемые сценарии.**

1. Создать диалог, добавить текстовый ход и screenshot; сообщения сохраняются автоматически после отправки и во время длинного ответа с ограниченной частотой записи, а финальный статус/текст — при завершении. Перезапуск браузера/extension page восстанавливает порядок и связи.
2. Истечение или перевыпуск анонимного серверного токена не удаляет и не меняет локальную историю: идентичность сессии и владение локальными диалогами разделены.
3. Старые записи настроек читаются после миграции; неизвестные поля не повреждают диалоги.
4. Удаление диалога освобождает его вложения, если ими не пользуются другие записи.
5. Quota/storage failure не показывает ложное состояние «сохранено», не удаляет молча существующие данные и сообщает об ошибке.
6. Ограничение размера/срока хранения выполняется явно и без скрытой потери неэкспортированных данных.

**Проверка:** isolated browser/profile, storage migration fixture и reopen/delete сценарии; без сетевого API. **Блокирует:** D-06 — local retention/delete/export/incognito policy. **Зависимости:** TD-01 по решениям; TD-04 и TD-05 используют сохранённую модель. **Рекомендация выбора хранилища:** IndexedDB, не принято до проверки целевой платформы.

<a id="td-04"></a>
### TD-04. Жизненный цикл панели и диалога

**Приоритет:** P1 · **Статус:** завершено · **Результат:** пользователь может свернуть большую панель до компактной видимой кнопки/значка, вернуться к тому же диалогу, закрыть его с сохранением и осознанно начать новый.

**Зачем.** Текущая кнопка close удаляет iframe, а не просто скрывает панель. Новый захват обновляет действующий iframe только пока он открыт; fallback popup — отдельное окно и отдельная память.

**Объём.** Определить состояния «свернута/видна/закрыта», список недавних диалогов и точки повторного открытия. Рекомендация для сворачивания — оставить на странице небольшой видимый значок с индикатором ответа, по нажатию восстановить тот же `dialogId`; расположение, перетаскивание, один значок или значки для нескольких диалогов — не принято. Согласовать выбор диалога и захвата при нескольких вкладках/окнах. Описать перезагрузку страницы, переход, повторное открытие, popup fallback и разрешения. Уточнить поток генерации при сворачивании, закрытии, удалении диалога и смене страницы.

**Не входит.** Обязательный Chrome Side Panel, глобальное permission на все страницы, новый toolbar возле каждого выделения и макет всего приложения. Любые новые permission должны обосновываться отдельно.

**Действия и ожидаемое поведение (предлагаемый контракт, ещё не принятое решение).**

| Действие | Ожидаемое поведение |
|---|---|
| Свернуть | Большая панель исчезает, остаётся компактная видимая кнопка/значок; активный ответ следует D-07. |
| Вернуть | Нажатие на значок показывает тот же `dialogId`, историю и состояние ответа. |
| Закрыть | Убирает панель и сохраняет диалог; останавливает или продолжает генерацию согласно D-07. |
| Новый диалог | Создаёт пустой `dialogId`; не подменяет сохранённые сообщения старого диалога. |
| Удалить | Удаляет выбранный диалог/вложения по D-06; случайное удаление подтверждается до потери данных. |

**Проверяемые сценарии.**

1. Сценарий: в диалоге A есть три текстовых сообщения и изображение; свернуть панель — на странице остаётся доступный с клавиатуры видимый значок с доступным именем и состоянием генерации; нажатие восстанавливает тот же `dialogId`, три сообщения и вложение.
2. Закрыть с выбранной политикой не теряет сохранённые ходы; удаление отдельного диалога показывает последствия и освобождает место.
3. Новый capture продолжает выбранный диалог либо создаёт новый согласно D-08a; это видно до изменения контекста.
4. Popup fallback согласован с панелью и не создаёт неожиданную вторую копию диалога.
5. Перезагрузка/навигация страницы, закрытие вкладки, перезапуск браузера, повторный запуск расширения и stream во время каждого действия проверены отдельно; выбранное поведение соответствует D-08c.
6. Проверены выбранный в D-08b вариант значка/списка на небольшом экране, положение/перетаскивание и клавиатурный доступ; панель не перекрывает критичный контент.

**Проверка:** браузерные сценарии с несколькими вкладками/окнами, перезагрузкой extension page и управлением клавиатурой; подменный transport для генерации. **Блокируют:** D-07, D-08a, D-08b и D-08c. **Зависимость:** TD-03.

<a id="td-05"></a>
### TD-05. Контекст запроса и контроль роста истории

**Приоритет:** P1 · **Статус:** завершено · **Результат:** transcript сохраняет историю, а каждый provider request получает осознанно собранный ограниченный контекст.

**Зачем.** Сейчас каждый запрос содержит всю `history`; к каждому новому пользовательскому ходу снова добавляется текущее изображение. Ограничение capture storage не ограничивает размер in-memory transcript или HTTP payload.

**Объём.** Ввести чистую границу `saved transcript → request context`. Зафиксировать лимит входных изображений/текста, дедупликацию attachment ID, удаление/замену старых image payload из контекста, и правило работы с длинным transcript. Не говорить модели, что старое изображение остаётся у провайдера между запросами: если оно нужно для ответа, его надо включить в соответствующий запрос или сформировать проверенное описание/summary. При summarization сохранять исходную задачу и попытку студента как источник истины; помечать summary как производное и восстанавливаемое.

**Не входит.** Не обещать точную «память модели», бесконечный контекст, автоматическую OCR-достоверность или безошибочные summary.

**Проверяемые сценарии.**

1. Новый ход не дублирует неизменённый screenshot, если он не нужен по согласованному правилу; новые captures остаются связаны со своими вопросами.
2. Многошаговый диалог превышает выбранный порог: предыдущие пользовательские условия и собственная попытка ученика не исчезают молча.
3. Изображение больше установленного предела блокируется до сети с объяснением, либо обрабатывается согласованным безопасным вариантом.
4. Повторный запрос/«Проще» получает именно тот контекст, который UI обещает; после удаления image attachment дальнейший запрос не отправляет скрытую копию.
5. Отказ/прерывание при сборке контекста не портит исходный сохранённый transcript.

**Проверка:** сериализованный mock request snapshot для 1/нескольких изображений, длинного диалога, retry и missing attachment; без платного API. **Блокируют:** D-09. **Зависимости:** TD-03, решения TD-01; UX-интеграция зависит от TD-04.

<a id="td-06"></a>
### TD-06. Анонимный шлюз и серверная защита общего ключа

**Приоритет:** P1 · **Статус:** реализация в backend loop · **Результат:** ключ OpenRouter и обязательные лимиты находятся на сервере; локальная история и usage — в браузере. Утверждённый контракт от 2026-10-16 заменяет прежние предложения о денежном cap, нескольких экземплярах, подписанном JWT и обязательной серверной статистике. См. [текущий backend loop](#backend-resume-20261016).

**DECISION — минимальный принятый объём.**

- Один процесс Node.js/TypeScript и SQLite на persistent disk; multi-instance не поддерживается. Ключ OpenRouter — только runtime env сервера. Сохраняются текущие модели, fallback и per-task output caps512–2048.
- Сервер выдаёт случайный bearer на30дней, хранит только hash. Renewal сохраняет identity и cooldown. Выдача20/IP/час, short-lived HMAC buckets; сырой IP в БД/обычных app logs не хранится. Только явно доверенный proxy peer может передать клиентский адрес. Anonymous session не является аккаунтом/личностью, NAT делит лимит выдачи.
- Атомарно: один принятый start/10сек на сессию, один in-flight/сессию, четыре globally, без скрытой очереди. Stop не снимает cooldown. Availability fallback до output относится к одной операции; неоднозначный/partial сбой не запускает платный повтор. Explicit Retry получает новый request ID.
- Клиент выбирает ограниченный контекст общим приблизительным estimator; сервер создаёт canonical system/task prompt и повторно проверяет точный отправляемый payload. Номинально200к input с резервом20к; это не native-token hard bound. Только выбранные user/assistant messages и нужные изображения уходят на сервер; excluded history и черновик по клавишам не загружаются.
- HTTP32MiB; image4MiB decoded, PNG/JPEG/WebP с bounded dimensions; arbitrary URL fetch отсутствует. Server-owned модели/endpoint/параметры, timeout180сек. Context refusal остаётся явным и не запускает fallback.
- В SQLite только sessions/issuance/cooldown и request ID/fingerprint/status/timestamps. Без prompt/image/ответов и подробного per-chat usage. Idempotency window24часа, очистка при startup/активности; истёкшие session удаляются, незавершённые операции после рестарта помечаются interrupted. Повтор ID не создаёт новую генерацию в том же24-часовом окне; конфликт payload отклоняется.
- SSE сохраняет stream, Stop, fallback/finish/usage. Browser сохраняет partial и финальный usage в существующем Turn.usage; отсутствие usage — unknown. Backend запрашивает upstream cancellation, но уже обработанное может быть оплачено.

**Не входит.** Денежный cap, reserves и daily token quota не приняты; не вводить их как новый gate. Rate/context/output/concurrency уменьшают нагрузку, но не задают денежный потолок и не исключают abuse. Нет accounts/billing/cloud history/уникальной личности, production deployment или публикации магазина.

**Проверка.** Fake HTTP/SQLite boundary: admission/races/cooldown/restart/idempotency, role/schema/image/body/model/params, trusted proxy, CORS, stream/final usage, timeout/disconnect, отсутствие контента/ключа в storage/logs. Chromium→настоящий backend→fake upstream, preview/payload match, сохранение local usage/partial, прежний UI. Primary-only allowance≤3 реальных попытки, включая fallback, на synthetic fixture; worker0. Инструкции запуска/health/stop/rollback — docs/backend-deployment.md. Статус итоговой приёмки и commit/evidence map — в начале файла/ledger.

<a id="td-07"></a>
### TD-07. Границы ответа и отказоустойчивость потока

**Приоритет:** P2 · **Статус:** завершено · **Результат:** интерфейс отличает нормальный конец, пустой ответ, отмену и сбой; partial text не маскируется под полный результат.

**Зачем.** Текущий API слой разбирает SSE по одинарным `data:` строкам, отменяет поток `AbortController` и различает типы ошибок. Для последующих stream UX и retries нужны наблюдаемые критерии завершения и проверка границ.

**Объём.** Зафиксировать причину/статус завершения, длину частичного ответа, отмену, EOF/ошибку соединения, повтор/fallback и визуальное различие неполного/полного результата. Разбирать provider `finish_reason` (включая `stop`, `length`, `error`), SSE-ошибки внутри HTTP 200 и чистый EOF без terminal-события. Последний случай должен завершаться статусом «оборвано», не «готово». Предусмотреть статусы как минимум `complete`, `truncated`, `interrupted`, `cancelled`, `provider_error`. Не делать безусловный повтор после неоднозначного обрыва: это может удвоить расходы. Не менять уже имеющиеся per-turn `max_tokens`/`temperature` как будто их нет. Определить, какие ограниченные метаданные ответа полезны для сравнения/проверки качества, не показывая пользователю обязательный выбор модели.

**Проверяемые сценарии.**

1. Mock SSE разбит на произвольные chunks, включая разрез внутри `data:`; UI собирает тот же текст.
2. Empty reply, malformed JSON, HTTP error, aborted request и interrupted stream имеют разные понятные состояния.
3. Partial answer не получает визуальный статус «полностью проверен»; повтор не добавляет два одинаковых хода и не запускается автоматически без согласованного правила.
4. Очень длинный ответ обрывается по существующему per-turn бюджету и явно показывает предел/продолжение только если оно реализовано.
5. Текст ошибки не содержит Authorization header, API key или чувствительный URL.
6. Provider завершает stream с `finish_reason=length`, присылает event-level error при HTTP 200 или закрывает соединение без terminal event: каждый вариант получает соответствующий неполный/ошибочный статус и не выглядит как успешный полный ответ.

**Проверка:** fixtures для SSE/JSON, mock provider, без real API. **Зависимости:** TD-05; retry semantics согласовать с D-03 и D-07.

<a id="td-08"></a>
### TD-08. Подсказка и проверка решения ученика

**Приоритет:** P1 · **Статус:** завершено · **Результат:** пользователь может запросить следующую подсказку и проверить собственную попытку; приложение не выдаёт полный ответ вместо учебного взаимодействия по умолчанию.

**Зачем.** Текущее направление явно включает подсказки и проверку своего решения. Сейчас доступны Solve/Quiz/Explain/Translate/Summarize/Ask и действие «Проще»; `Hint` и `Check my work` отсутствуют.

**Объём.** Сделать отдельные сценарии, а не только переименовать Solve. Для Hint — одна ограниченная подсказка/наводящий вопрос, затем ожидание ученика; дальнейшие подсказки являются следующими ходами. Для Check — явное поле попытки ученика или добавление выделения/ответа; объяснить, что проверяется, назвать первую обнаруженную ошибку и дать исправляющий намёк. Связать попытку с изображением/условием. Полный ответ — только по явному действию или принятому решению.

**Не входит.** Автоматическая оценка школьного уровня из поведения, публичный рейтинг, бесконечный tutor loop или скрытое сохранение профиля.

**Проверяемые сценарии.**

1. Hint на читаемом условии не раскрывает конечный ответ в первом ходе; на неразборчивом изображении просит уточнить ввод.
2. Check получает и условие, и попытку ученика; различает корректную попытку и конкретный первый неверный переход на фикстурах.
   Примеры для проверки предложенного поведения: Hint для `2x+6=10` предлагает убрать постоянное слагаемое, не называет `x`; Check для попытки `2(x+3)=10 → 2x+3=10` показывает первую ошибку раскрытия скобок, не выдавая вместо анализа полное решение.
3. «Показать решение» доступно как явный путь и не переписывает ранее данную попытку.
4. Повторный ход сохраняет исходное условие и полный student input в рамках TD-05 context policy.
5. RU/EN и явно выбранный язык ответа дают непротиворечивый формат; ошибки не приписывают ученику то, чего он не отправлял.

**Проверка:** шаблонные prompt assertions и небольшая обезличенная fixture matrix; real API оценка качества — отдельная опциональная работа с разрешённым бюджетом. **Блокирует:** D-10; initial audience/subjects уточнить в D-11. **Зависимости:** TD-05 контекст, базовый TD-07 error state; Hint/Check можно независимо проектировать до локальной истории.

<a id="td-09"></a>
### TD-09. Повторение ошибок и учебная практика

**Приоритет:** P3 · **Статус:** ожидает решения · **Результат:** ограниченный сценарий возвращения к прошлой ошибке, только если пользователю понятна его ценность и история достаточно надёжна.

**Зачем.** «History / review mistakes» и Practice more могут поддержать долговременную учебную задачу, но user direction пока не фиксирует аудиторию, дисциплины, сроки или способ определения ошибки.

**Объём.** После TD-03/TD-08 выбрать одну маленькую проверяемую задачу: открыть прежний диалог, вручную отметить ошибку, либо попросить похожий пример. Сохранять связь с исходным решением. Уровень студента может задаваться явно и меняться пользователем; не делать его выводом из всех сообщений.

**Не входит.** Автоматический долговременный student profile, поведенческий скоринг, Study plan/Exam cram, Flashcards, рейтинги/серии занятий и претензия на персональный tutor без проверки.

**Проверяемые сценарии.**

1. Пользователь может открыть ранее сохранённый пример и понять, почему он помечен.
2. Повторное упражнение сохраняет исходную задачу отдельно от сгенерированного примера.
3. Удаление исходного диалога следует согласованным правилам связанных карточек/упражнений.
4. Никакой уровень или профиль не создаётся без явного ввода/решения хранения.

**Проверка:** локальные фикстуры и сценарии удаления/повтора, без реального API. **Блокируют:** D-06, D-11; **зависимости:** TD-03 и базовый TD-08.

### TD-10. Проверки качества и минимальная диагностика

**Приоритет:** P2 · **Статус:** завершено · **Результат:** повторяемая проверка истории, gateway, rate contract и tutor workflows без обязательных платных вызовов. Здесь только локальный rate contract; trusted server contract остаётся в TD-06.

**Объём.** Разнести mock/fixture проверки и опциональное real-provider качество. Покрыть свежий старт, сохранение/reopen, миграцию настроек, удаление, multiple captures, image dedupe, cross-language, long context/truncation, rate boundary, two windows, retry/abort, malformed/partial SSE, fallback и missing crop. Для метрик определить минимум: локальные агрегаты без содержимого либо отдельный opt-in telemetry. Любая telemetry требует D-12.

**Не входит.** Запуск `quality`, `compare`, любых real API calls, сбор изображений пользователя и отправка transcript телеметрии по умолчанию.

**Проверяемые сценарии.**

2. Строки тестовых запросов не содержат реальные пользовательские screenshot или credentials.
3. При включённом реальном API тест явно помечен как платный/внешний и запускается отдельно.
4. Любой локальный usage metric сбрасывается/удаляется по документированному действию и не создаёт скрытую identity.

**Проверка:** каждый реализуемый срез получает подходящие unit/extension integration fixtures; real API evaluation — только если явно входит в авторизованный объём с известным бюджетом. **Блокируют:** D-12 для необязательной внешней аналитики; mock test architecture можно начать без неё.

## Реестр решений

Здесь только решения, которые меняют несколько дальнейших задач либо определяют видимый продукт/доверенную границу. Рекомендации — предложения для обсуждения.

### D-01. Кто получает доступ без видимой регистрации?

**DECISION (2026-10-16):** целевая самостоятельная установка без аккаунта; для доступа к gateway используется anonymous bearer session. Локальный loop не публикует сервис/расширение. Публичная доставка следует после выбора hosting/domain и отдельного deployment.

### D-02. Кто размещает gateway?

**DECISION (2026-10-16):** свой минимальный Node/TypeScript gateway + SQLite, один экземпляр; локальная разработка и проверка сейчас. **OPEN:** публичный host/domain и эксплуатационный запуск. Это не blocker локальной реализации; Fozzy/managed service не выбраны. Инструкция запуска/прокси/отката находится в docs/backend-deployment.md.

### D-03. Что ограничивают10секунд и Retry?

**DECISION (2026-10-16):** один принятый start/10сек на сессию по серверному времени, один in-flight/сессию, четыре globally. Genuine availability fallback до output входит в одну операцию. Same request ID в24часа не запускает второй model start; explicit Retry/Regenerate — новый ID. Stop не сбрасывает cooldown. Сохранение/History/minimize не являются генерациями. Никакой скрытой очереди или платного automatic retry после ambiguous/partial failure.

### D-04. Как выдавать anonymous session?

**DECISION (2026-10-16):** random bearer30дней, token hash в SQLite; renewal сохраняет token/identity и лимиты, что избегает межвкладочной ротационной гонки. Выдача20/IP/час, short-lived HMAC IP buckets, trusted proxy allowlist. Это stateful серверная сессия, JWT не нужен. Сброс установки/смена сети возможны; session/IP не считаются личностью. Общее школьное/NAT-соединение делит лимит выдачи.

### D-05. Нужен ли monetary cap в текущем backend loop?

**DECISION (2026-10-16):** пользователь явно попросил не задавать сумму. Денежные cap/reserves и daily token quota не входят в утверждённую реализацию и не являются новым approval gate. Принятые rate/context/output/concurrency limits уменьшают нагрузку, но не задают денежный потолок и не гарантируют отсутствие abuse. Любое последующее изменение этой политики требует отдельного решения, а не молчаливого включения в scope. Сам loop ограничен≤3 реальными попытками primary, включая fallback; worker использует fake-only.

### D-06. Как долго хранить локальные диалоги и вложения?

- **A:** сохранять локально до явного удаления, показывать storage usage и предоставить delete/export.
- **B:** ограниченный срок/ёмкость с явной политикой очистки и предупреждением до удаления.
- **C:** не сохранять изображения после диалога, оставлять только текст.
- **Рекомендация:** A с явным Delete и настраиваемой очисткой; не синхронизировать облачно по умолчанию.
- **Затрагивает:** TD-03, TD-04, TD-05, TD-09, TD-11. **Блокирует:** миграцию и retention behavior.

### D-07. Что значит minimize/close во время ответа?

- **A:** minimize прячет окно и продолжает stream; close сохраняет transcript и отменяет текущий stream.
- **B:** и minimize, и close продолжают stream в фоне; отдельный Stop останавливает.
- **C:** любое закрытие отменяет stream, но диалог сохраняется.
- **Рекомендация:** A: ожидаемый смысл «скрыть» — не терять ответ, а закрытие — закончить активный запрос без потери истории.
- **Затрагивает:** TD-04, TD-07. **Блокирует:** точный UI и cancel lifecycle.

### D-08. Как пользователь выбирает диалог и связывает новый capture?

- **A:** продолжить открытый выбранный диалог; отдельное действие New chat начинает чистый контекст.
- **B:** каждый capture создаёт новый диалог с возможностью вручную добавить в другой.
- **C:** продолжать только если capture с той же вкладки/страницы.
- **Рекомендация:** A с явным отображением активного диалога; это ближе к требованию «вернуться к тому же контексту» и сохраняет контроль пользователя.
- **Затрагивает:** TD-03, TD-04, TD-05. **Блокирует:** UX нескольких вкладок/окон и связывание captures.

Подрешения, которые нужно закрыть в рамках этого вопроса:

- **D-08a:** продолжает ли новый capture выбранный открытый диалог или создаёт новый; как явно выбрать другой.
- **D-08b:** один общий значок/список или отдельные значки для нескольких диалогов; положение, перетаскивание и клавиатурная доступность.
- **D-08c:** что открывается при повторном запуске/нажатии горячей клавиши: последний диалог, выбор истории или новый диалог.

### D-09. Как строить контекст длинного диалога?

**DECISION (2026-10-16):** transcript/images остаются локально. Клиент выбирает ограниченные целые группы заданий общим приблизительным estimator, номинально200к input с резервом20к и1024/image; локального tokenizer нет. Внутренняя projection и видимые исключения соответствуют выбранному payload. Backend получает только выбранные сообщения, формирует canonical system/current-task prompt и проверяет ту же оценку; draft по клавишам и excluded history не отправляются. Нет автоматического summary, скрытой памяти провайдера и точного native-token обещания. Серверные payload/image guards и отказ провайдера остаются явными. Фактический usage — с ответом в браузере, отсутствующий usage unknown.

### D-10. Как выглядит первая версия Hint/Check my work?

- **A:** Hint выдаёт один следующий шаг; Check разбирает введённую попытку и указывает первую существенную ошибку; полный ответ доступен отдельно.
- **B:** сначала короткая диагностика, затем ученик сам выбирает Hint или полный разбор.
- **C:** только свободный вопрос, без новых режимов.
- **Рекомендация:** A: Hint предлагает следующий шаг; Check показывает первую существенную ошибку; полное решение доступно отдельно по явному действию. Например, для `2x+6=10` подсказка предлагает убрать постоянное слагаемое, не называет `x`. Для попытки `2(x+3)=10 → 2x+3=10` Check указывает первую ошибку раскрытия скобок и не выдаёт целиком готовое решение.
- **Затрагивает:** TD-08, TD-05, TD-10. **Блокирует:** UI contract и prompt acceptance.

### D-11. Для кого и каких предметов проектирует первая учебная версия?

- **A:** базовые задания по математике/читаемому скриншоту, без выводимого уровня ученика.
- **B:** несколько явно выбранных предметов/уровней, которые пользователь может поменять.
- **C:** оставить широкий текущий vision tutor, валидировать ограниченный набор задач.
- **Рекомендация:** C для первого шага с явным disclosure ограничений; выбрать реальные fixtures до обещания универсальности.
- **Затрагивает:** TD-08, TD-09, TD-10, TD-11. **Блокирует:** только широкие product claims и постоянную personalization.

### D-12. Какие метаданные/аналитика допустимы?

- **A:** только локальные агрегаты на устройстве, без prompt/image.
- **B:** opt-in серверные счётчики без содержимого, сроки и поля публично описаны.
- **C:** пока никакой аналитики.
- **Рекомендация:** C для необязательной аналитики до появления ясного вопроса; затем рассмотреть A. Это не запрещает минимальное operational state, нужное для серверного лимитера, идемпотентности и контроля расхода в TD-06. Не собирать историю диалогов/изображения как аналитику без отдельной политики и решения.
- **Затрагивает:** TD-03, TD-06, TD-07, TD-10, TD-11. **Блокирует:** server telemetry и хранение provider metadata, не локальные mock tests.

Проверено 2026-10-19 на `88680fd60d6cf07a364ee62ed83ad7024be08d0c` (`work/study-buddy-luna-prompts-2026-10-19`). Это code-based карта, не визуальная приёмка UI. Решения в разделе рекомендаций — HYPOTHESIS/OPEN.

## Вывод по текущему поведению

**FACT.** В этом срезе кнопки и `Turn.kind` сохранились, но app-generated текстовые инструкции пусты (`src/shared/prompts/index.ts:19-37`). Gateway task metadata содержит task, оба языка и input, однако `prepareGatewayGeneration` передаёт в provider только prepared `messages` и maxTokens, а последнее сообщение канонизирует в явный текст лишь для Ask и Check input (`src/shared/gateway-protocol.ts:23-40,63-89`). Upstream Chat Completions JSON включает model/messages/stream/stream_options/max_tokens; `temperature` не задан (`src/shared/api.ts:168-192`). Значит, Solve/Hint/Check/Explain/Quiz/Translate/Summarize/Simpler сейчас описывают UI intent, но сами не задают его модели. По коду нельзя заключить, что ответ следует учебной или сократической политике.

**FACT.** Существующая архитектура хранит `kind`, `input`, `replyTo`, локаль, assistant turns и capture attachment; она строит ограниченную projection истории, отображает исключённые сообщения и позволяет вернуть их действием Use again (`src/shared/conversations.ts:8-35,117-206`; `src/chat/chat.ts:493-524`). `replyTo` связывает assistant turn с исходным user turn (`src/chat/chat.ts:785`); он сам по себе не моделирует отдельную ученическую попытку и её связь с задачей. Новая система состояния не нужна, чтобы сначала определить и проверить semantics.

**FACT — что означает текущий Quiz:** интерфейс подписывает preset как “Multiple choice” / «Выбор ответа» (`src/shared/i18n.ts:99,225`; кнопка `src/chat/chat.html:33`). В текущем срезе `88680fd` его task template пуст, поэтому по нему нельзя заключать, что именно получит модель. Исторический шаблон Quiz разбирал правильный вариант и почему остальные неверны (`BACKLOG.md:172`); историческое описание адаптивного сценария говорит: если варианты видны — объяснить их, иначе решить задачу и отметить отсутствие видимых вариантов (`BACKLOG.md:189-191`). Это разбор предоставленного задания, не генерация нового теста.

**DECISION:** отдельное действие `Multiple choice` удаляется из целевого UI, а Solve разбирает предоставленные MCQ, включая правильный вариант/варианты и объяснение. Это решение для будущего runtime-среза; наблюдавшаяся в коде кнопка и локализация остаются фактом исторического среза `88680fd`. Генерация новых вопросов/практики Quiz отложена; сначала довести базовые функции до высокого качества и улучшать постепенно. Исторические Quiz turns/kinds и transcript сохраняются, их массовое удаление или переписывание не требуется.

Контекст объединяет turns по задаче/изображению, исключает незавершённые и устаревшие ответы, выбирает свежие целые группы в пределах приблизительной оценки; старые user text/image можно вернуть вручную (`src/shared/conversations.ts:117-206`; `src/chat/chat.ts:493-524`). `contextTurnText` включает только Ask/Check input, не старые task prompts (`src/shared/conversations.ts:275-279`). Поэтому **исторические GPT-4.1-era** [`docs/prompts-research.md`](prompts-research.md) и примеры качества [`docs/prompts-quality/`](prompts-quality/) не описывают текущий запрос. В частности старый документ рекомендует `temperature=0`; фактически температура не отправляется. Актуальный DECISION этапа 1–2 прямо фиксирует отсутствие явных temperature/reasoning параметров (`ToDo.md:6-16`, FACT этапа 1 `:29-33`; решение подтверждается этапом 2 `:35-41`). Противоречащее утверждение в `ToDo.md:222-232` принадлежит явно помеченному исходному состоянию на 2026-10-06 до loop (`ToDo.md:222-224`) и устарело; это исторический baseline, не действующая спецификация.

## Технические факты

- OpenAI model card описывает GPT-6 Luna как general-purpose efficient model; image input поддерживается, text — input/output. Карточка сообщает image input, контекст 1,050,000 и max output 128,000; это свойства модели/API, не качество tutoring и не обещание решения заданий. Приложение выбирает max_tokens=16,384, то есть задаёт собственный меньший лимит ответа. Сейчас приложение использует OpenRouter ID `openai/gpt-6-luna`, max_tokens 16,384, не задаёт temperature (`src/shared/ai.ts:7-12`; `src/shared/prompts/index.ts:39-54`). Карточка указывает fine-tuning unsupported.
- OpenRouter Chat Completions и models catalog документируют совместимый request shape и свойства конкретных моделей. Для фактического запроса этого приложения первичны его own `src/shared/api.ts` и серверная подготовка `src/backend/app.ts:252-269`; каталог не доказывает корректность поведения модели.
- **HYPOTHESIS:** начать с intent-контракта и оценок на реальных типах входа, не добавляя tools, fine-tuning, RAG, learner profile или multi-agent. OpenAI model optimization guide поддерживает цикл: зафиксировать baseline на representative inputs, задать ясные инструкции/контекст, повторять измерение. Она отдельно говорит о недетерминизме и меняющемся behavior snapshots. Применять этот общий принцип можно без hosted eval API.

## От general-модели к специализированному помощнику

**FACT:** GPT-6 Luna — базовая general-purpose модель с image input; специализация Study Buddy должна появиться в прикладном слое, который сейчас отключён. Её можно строить из согласованных инструкций (что означает intent), grounding-контекста, userflow/state, формата feedback/output и оценки поведения; это не требует менять веса модели. Сопоставление с существующей архитектурой:

| Слой помощника | Что он задаёт | Существующая опора / что сейчас отсутствует |
|---|---|---|
| Intent/instructions | Роль, intent Solve/Hint/Check и желаемое действие ответа | `Turn.kind` и prompt compatibility seams уже есть, но строки инструкций сейчас пусты (`src/shared/prompts/index.ts:19-37`). |
| Grounding context | Задача, выбранные turns и изображения, язык ответа | Context projection и raw Ask/Check/image messages уже формируются (`src/shared/conversations.ts:117-206,249-279`). Языки хранятся и приходят в gateway metadata, но не включены в provider messages (`src/shared/settings.ts:4-38`; `src/shared/gateway-protocol.ts:63-89`). |
| Userflow/state | Где ученик отвечает, как повторить/продолжить, к чему привязать действие | Существуют turns/history, Ask composer, Retry, Reuse, Stop. Учебный цикл Check/Quiz и выбранная цель Simpler не определены новым контрактом. |
| Output/feedback | Формат решения, точность проверки, следующий шаг/feedback | Сейчас это не задаётся действующей инструкцией; модель получает выбранные сообщения. |
| Evaluation | Корректность, соблюдение intent, UX и самостоятельное применение | Есть исторические prompt quality notes/фикстуры, но они относятся к прежнему prompt+модельному этапу; новая политика и её eval matrix ещё не утверждены. |

Официальный [vision guide: limitations](https://developers.openai.com/api/docs/guides/images-vision#limitations) отдельно отмечает общие риски чтения мелкого текста, интерпретации линий/стилей и пространственной локализации, а также неверных описаний изображений. Это не измеренная частота ошибок именно GPT-6 Luna. Для screenshot geometry eval следует раздельно оценивать чтение условия/обозначений и математическое решение: tutor-role instruction сама по себе не устраняет perception errors.

Это разделение помогает отличить general модель от специализированного поведения приложения. **HYPOTHESIS:** сначала исследовать сочетание компактных инструкций и существующего контекста/flows; инструменты, fine-tuning, RAG, learner profile и multi-agent остаются опциональными архитектурными выборами, а не prerequisite. Kestin et al. дают узкий практический пример, где одного prompt не хватало для надёжной последовательности multi-part задач и её закодировали в платформенном flow.

## Эмпирическая опора и её пределы

- **Самообъяснение.** Chi et al. (1994), эксперимент с учащимися, изучающими объяснение кровообращения, связывает содержательные self-explanations с лучшим пониманием сложных вопросов. Aleven & Koedinger (2002), две classroom studies Cognitive Tutor, нашли лучшее понимание и transfer-задачи, когда учащиеся объясняли шаги решения. Это поддерживает возможность попросить пользователя объяснить свой шаг; это не доказывает, что любое LLM-объяснение улучшает learning.
- **Retrieval.** Roediger & Karpicke (2006): в двух экспериментах со студентами и прозой свободное воспроизведение дало преимущество перед повторным изучением на отложенных проверках 2 дня/1 неделя, хотя на 5-минутной проверке повторное изучение было лучше. van den Broek et al. (2025) рандомизировали участников в stepwise worked examples с/без попытки предсказать следующий небольшой шаг; после ответа участник видел шаг как feedback и мог его перечитать. Через неделю выросли recall процедуры и problem-solving. Это обученный, сегментированный формат; он занимал больше времени и не равен действию разбора предоставленного multiple-choice задания.
- **LLM outcomes.** Bastani et al., PNAS 2025, field RCT почти с 1000 школьников по математике: GPT-4 помогал решать practice problems, однако снятие AI access выявило риск худшей независимой экзаменационной работы при обычном чате. GPT Tutor смягчал ущерб. Важная граница: Tutor менял поведение и давал учительские правильные решения, типовые ошибки и подсказки; результат не изолирует эффект одной system prompt. Outcome — ближайшие экзамены, не долговременная retention.
- Kestin et al., Scientific Reports 2025: crossover RCT (N=194) со студентами вводной физики Harvard сравнивал два урока с одинаковым содержанием, AI tutor и активный класс; сообщён лучший немедленный post-test результат и меньшее время в AI-условии. Это был связанный пакет: prompt, материалы/видео, авторские content-rich ответы и платформа, проходящая задачи по порядку. Авторы пишут, что prompt не гарантировал последовательность в многосоставных заданиях; результат не измеряет долгосрочную retention и не доказывает эффект одного prompt.

**Продуктовый вывод — HYPOTHESIS.** Evidence поддерживает возможность выбора между worked example, подсказкой, попыткой объяснить свой шаг и повторной практикой. Она не требует запретить прямое решение, заставлять всех идти сократически или считать assisted completion доказательством обучения. Быстрый ответ тоже может быть сознательным пользовательским намерением.

4. Генерация нового набора Quiz отложена. Сначала решить, нужен ли отдельный `Multiple choice` для разбора предоставленного MCQ или такой разбор должен покрываться Solve; судьба текущей кнопки остаётся OPEN. Возможный цикл сгенерированной практики не проектируется в этом срезе.
5. Язык: решить ожидаемое поведение `auto`; затем отразить его в явном wire-level instruction contract. Сейчас настройка не ограничивает текст модели.
6. До теста поведения собирать матрицу: correctness (ответ/ошибка/нечитаемый кроп), pedagogy (соответствие выбранному intent, качество feedback), UX (языки, follow-up/retry/reuse/stop, прямой ответ), learning (самостоятельная похожая задача без модели; delayed test только в отдельном исследовании). Assisted success и independent transfer/retention — отдельные показатели.

## Первый decision point

**DECISION — Solve сразу выдаёт полное решение с объяснением.** Пользователь выбрал вариант A (первый вариант). Предварительная попытка не обязательна, обязательная практика не добавляется. Возможность необязательной практики после ответа остаётся OPEN. Факт текущего среза: кнопка сохраняет task kind, но не передаёт инструкции модели; это решение задаёт продуктовый смысл будущего поведения, а не текст prompt.

Рассмотренные варианты: (1) прямой worked example с полным разбором — **принят**; (2) требовать попытку до решения — не выбран; (3) спрашивать перед ответом, показать решение или начать с подсказки — не выбран. Ранее упомянутая рекомендация по добровольной практике не означает, что такая возможность уже утверждена. Точная формулировка инструкций и формат ответа остаются OPEN; answer-first формат не задан.

**DECISION — Hint выдаёт одну полезную подсказку за раз**, описывающую подход или следующий шаг. Повторный Hint учитывает ранее выданные подсказки и становится конкретнее; глубину помощи контролирует пользователь. Полное решение запрашивается через Solve или явную просьбу в чате; Hint остаётся форматом подсказок. Обязательная попытка перед Hint не вводится. Факт текущего среза: `Turn.kind` отмечает Hint, но инструкция модели отсутствует; точная формулировка prompt остаётся открытой.

**Другие DECISION по режимам и языкам.** Explain предназначен для объяснения понятий, обозначений или подхода и не обязан выдавать полное решение. Simpler нацелен на выбранный пользователем ответ; при реализации запрос должен получить target answer ID. Summarize охватывает текущее изображение/материал или явно переданный текст, а не весь чат по умолчанию. Check проверяет видимую работу на изображении без отдельной формы; текстовую попытку пользователь может изложить через Ask.

Генерация новых вопросов/практики Quiz отложена; ранее выбранный вариант B (пакет вопросов) относился только к возможной будущей функции и не является текущим scope. Принято убрать отдельную кнопку Multiple choice, а разбор предоставленного MCQ выполнять через Solve. Исторические Quiz turns/kinds остаются совместимыми в сохранённом transcript; удалять или переписывать историю не требуется.

`answerLanguage=auto` определяется языком браузера, независимо от `uiLanguage`, последнего сообщения и изображения. Явная просьба о языке применяется только к текущему ответу и не меняет настройку. Translate использует явно выбранный язык ответов агента, либо язык браузера при `auto`: английский источник при русском target сразу переводится на русский; если источник уже на целевом (эффективном) языке, агент спрашивает целевой язык. Приоритет `navigator.language`/`navigator.languages` и fallback для неподдерживаемого языка OPEN.

Выбраны общие ролевые/согласованные инструкции плюс отдельные инструкции задач; точные тексты не утверждены. Solve не запускает автоматическое предложение практики; Quiz, если будет сохранён, явно запускается пользователем. Заголовок создаётся вместе с первым ответом без отдельного платного вызова; текст/схема не утверждены.

Дальше OPEN: точные тексты общих/task/title инструкций для пользовательского review/approval. Детали браузерного language preference/fallback проверить при реализации как инженерные вопросы, не отдельный продуктовый gate.
